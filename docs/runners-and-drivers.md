# Драйверы и обработчики очередей (1.4.0)

## Резюме

Раньше выбор был размазан: `sync` числился драйвером, режим работы задавался только константами
(`WP_QUEUE_RUNTIME_MODE`, `WP_QUEUE_LOOPBACK`), а при каждом dispatch одновременно могли сработать
WP-Cron, `spawn_cron()` и loopback. С 1.4.0:

* **Драйвер** — только хранилище: `database` (по умолчанию), `redis`, `memcached`.
* **Обработчик** — ровно один из `daemon`, `loopback`, `wp_cron`, `sync`; по умолчанию `auto`.
  Невыбранные обработчики не регистрируют хуки (`wp_queue_process`, `wp_ajax_nopriv_wp_queue_loopback`)
  и не шлют запросов. Глобальная блокировка воркера из 1.3.0 остаётся страховкой.
* `auto`: `daemon`, если heartbeat `wp queue work` свежее 10 минут; иначе `loopback`
  (если проверка admin-ajax не провалилась и loopback не выключен константой), затем `wp_cron`
  (если нет `DISABLE_WP_CRON`), затем `sync`. В админке показан фактический обработчик и причина.
* `wp queue work` в ручном режиме `loopback`/`wp_cron`/`sync` пропускает работу (только записывает heartbeat),
  `--force` — обработать всё равно.

## Где хранится выбор

Приоритет: константа → опция `wp_queue_settings` → значение по умолчанию.

| Источник | Как выглядит в админке |
|----------|-----------------------|
| Константа вне блока плагина | поле заблокировано, «задано в wp-config.php» |
| Константа в блоке `// BEGIN WP Queue … // END WP Queue` | редактируется из админки, плагин переписывает блок |
| Опция | «выбрано в админке» |

Константы: `WP_QUEUE_DRIVER`, `WP_QUEUE_RUNNER`; старые `WP_QUEUE_RUNTIME_MODE` (`daemon`, `cron_loopback`)
и `WP_QUEUE_LOOPBACK=false` продолжают работать.

Запись блока (`ConfigFile::write`): только имена `WP_QUEUE_*`, значения экранируются; временный файл
рядом с wp-config.php, сохранение владельца/группы/прав (иначе отказ), проверка синтаксиса,
атомарный `rename`, сброс opcache, проверка загрузки WordPress через admin-ajax (`wp_queue_config_probe`
с одноразовым токеном). При ошибке — откат из бэкапа, при успехе бэкап удаляется. Если файл или каталог
недоступен для записи (или wp-config смонтирован read-only), админка показывает блок для ручной вставки.
Все действия — `manage_options` + nonce.

## Смена драйвера

Решение: **переносить задачи**, а не запрещать смену при непустой очереди — на живом сайте очередь
почти никогда не пуста, запрет сделал бы переключение невозможным.

* Перенос (`DriverSwitcher`) идёт под глобальной блокировкой воркера; если воркер работает или есть
  зарезервированные задачи — отказ «попробуйте через минуту».
* Переносятся готовые и отложенные задачи (остаток задержки сохраняется), пачками по 200; при ошибке
  задачи возвращаются обратно.
* Задачи, которые параллельные запросы успели положить в старый драйвер, воркер дотягивает в течение суток
  (`wp_queue_previous_driver`).
* Memcached не умеет перечислять задачи, поэтому уйти с него можно только при пустой очереди.

## Redis

Драйвер переписан на Lua-скриптах: `ready` list, `delayed` и `reserved` zset, `data` hash.
POP атомарно переносит созревшие отложенные и зависшие (> 300 с) зарезервированные задачи и резервирует
одну. Работает через phpredis и Predis (Redis Object Cache). Старые ключи `jobs:{queue}` импортируются.
Тест: 4 параллельных процесса × 120 задач — каждая выполнена ровно один раз.

## Прочее

* Проверка loopback в «Состоянии» теперь ходит в admin-ajax (`wp_queue_ping`), а не в wp-cron.php
  (раньше она запускала все просроченные события WP-Cron).
* В списке очередей видны все известные очереди, включая пустые (реестр `wp_queue_known_queues` + логи).
* В режиме `wp_cron` из WP-CLI `spawn_cron()` не вызывается (запрос терялся, а его блокировка держала WP-Cron минуту).
* Loopback: после серии dispatch в одном запросе воркер «пинается» ещё раз на shutdown.

## План проверки

1. Unit: phpredis и Predis с Redis, без Redis (CI: сервис redis:7).
2. Тестовый стенд WordPress + MySQL + Redis: «Сделать активным» Redis с записью блока в wp-config,
   перенос 255 задач, откат на Database (файл побайтно совпал с исходным); auto → daemon / loopback /
   wp_cron; ручной WP-Cron и sync; в режиме daemon нет loopback и wp-cron запросов.
3. Прод rwsite: Database + daemon (системный cron), константы перенесены в опцию.
